## Новый вывод

### P1 — изменённое тело запроса повторно отправляется с тем же operation_id; replay может ложно завершить частичный перерасчёт

UI-доказательство: `frontend/src/admin/sahifalar/PereraschetFakt.tsx:57, 86-120`.

`operationId.current.a/b` создаются один раз и обновляются только после общего успешного возврата. Если storno уже создан, а создание повторного предъявления завершается ошибкой, обработчик сообщает, что storno создан, и оставляет те же operation ID. Пользователь может поменять номер, формат или строки и повторить действие: код отправляет новое тело с прежним `operationId.a` (а иногда и `b`). Если первый ответ неизвестен, новый вариант тела также использует прежний ID.

Это опасно в сочетании с серверным replay. В предоставленных владельцем SELECT-only снимках `pg_get_functiondef` (`C:\Temp\PTO-C3-F2-WRITER-DEF-20261026.json`, `C:\Temp\PTO-C3-F2-BASE-DEF-20261026.json`) видно:

- `t2_akt_yarat` ищет существующий `t2_akt` по `operation_id` и немедленно возвращает `{ok:true,takror:true}`; сравнения тела запроса там нет.
- `t2_akt_yarat_v2` при `takror=true` немедленно возвращает результат до обновления `certified_*` полей.

Следовательно, если пользователь меняет тело между попытками, replay может подтвердить старую operatsiyani, не применив новый payload. В synthetic partial-retry probe storno получил успешный receipt, reissue вернул ошибку, затем пользователь сменил номер/формат/строки. Повторный запрос передал другое тело с тем же `operation_id`; mock ledger вернул replay `ok:true`, после чего UI вызвал `onYaratildi()` и показал общий success. Старый reissue не был создан в симуляции. Это означает, что только storno-qoralama может остаться, хотя интерфейс сообщает об успешном перерасчёте. Утверждение Ф-2 всё ещё требует отдельного действия владельца, но успешный статус способен подтолкнуть его к подтверждению неполной пары.

Второй строгий probe смоделировал неизвестный результат первого запроса: ledger сохранил возможный приём, клиент получил ошибку/таймаут, пользователь изменил строки и повторил. Новый payload снова ушёл с прежним ID; synthetic replay вернул `takror:true`, и UI перешёл к созданию второй части. API ledger был только тестовой моделью — БД в ходе C3 не вызывалась. Серверное поведение выше подтверждается именно переданными SELECT-only функциями, а не исполнением записи.

Строгие oracle в обоих probes требуют не переиспользовать operation ID для изменённого payload и не объявлять частичный старый набор завершённым по replay старого receipt. Оба oracle провалились.

**Рекомендация:** закреплять неизменяемый payload за каждым operation ID. После частичного успеха сохранять подтверждённый receipt и продолжать только оставшуюся часть с её исходным payload/ID; после неизвестного ответа запрещать редактирование и retry с новым телом до сверки receipt. При изменении номера/формата/строк создать новый attempt только после явной сверки уже созданных черновиков и их связи. Успех должен отражать обе части ожидаемой пары, а не только `ok:true` от replay.
