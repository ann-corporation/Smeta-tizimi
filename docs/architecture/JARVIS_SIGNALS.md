# Jarvis: компактные сигналы M5

## Что подключено

Существующий read dispatcher и существующий `agent-ish/javob_baho` направляют
фиксированные события в **существующий** `t2_osuvchi_yoz_v1/friksiya_yubor`.
Хранилище — `t2_friksiya`, SQL upsert-increment и настройки/лимиты прежние.
Новых таблиц, миграций, моделей и бизнес-команд нет.

`kasbQuvur` создаёт отдельную партию на запрос; десять существующих read tools
могут записывать события в неё. Повторные ключи суммируются в памяти. На выходе
из core выполняется не более одного RPC; Pages `waitUntil` сохраняет работу после
выдачи ответа. Тонкие адаптеры `agent-ish` (JSON/stream) и legacy `ai-savol`
передают lifecycle callback. Поэтому каналы, использующие их, получают один путь.
Без lifecycle callback flush ожидается; его потолок — 2 секунды, включая случай
транспорта, игнорирующего abort. Пустая партия не делает запроса.

## Значения и ограничения доказательств

- `read.<tool>` + `tugadi/t0…t4`: инструмент вернул результат; это **не** оценка
  правильности ответа и не end-to-end latency пользователя.
- `SOURCE_UNAVAILABLE`: dispatcher зафиксировал недоступность/исключение.
- `NO_ANSWER`: null результат или явно пустой поиск объектов.
- `FORBIDDEN`: ожидаемый отказ доступа, отдельная категория, не поломка.
- `feedback_good/bad/unclear`: существующая явная пользовательская оценка.

Результат остальных reader может содержать собственный текст «нет данных» без
машинного статуса. Он не угадывается по языку текста. Полная классификация всех
источников, новые MCP reads, chip clicks и correction events требуют дальнейшей
интеграции; этот шаг не объявляется завершением M5.

В counter payload нет вопроса/ответа, объекта, пути страницы, суммы, exception
message или произвольного кода. Только фиксированные коды, агрегат и серверные
actor/company в RPC envelope. `o=0`: число попыток не выдаётся за число людей.
Партия ≤60 ключей, число повторов ≤1000; SQL дополнительно ограничивает
компанию/день. Каждая партия имеет UUID; повтор flush использует тот же promise,
повтор явного feedback может передать тот же `operation_id`. Без стабильного
клиентского event ID повтор отдельного HTTP запроса не дедуплицируется.

Существующая отрицательная оценка также сохраняет прежний generic signal для
legacy weekly proposal pipeline. Новый counter payload не меняет прежний журнал
событий/историю и не утверждает, что всё приложение хранит только counters.

## Что остаётся для полного goal

Нет автоматического изменения поведения. Company aliases, routing/FAQ promotion,
глобальное k≥5, еженедельный отчёт и подтверждение человеком остаются отдельными
требованиями. Existing global prior threshold нельзя считать доказанным этим PR.
Production DB не изменена; live upsert/opt-out и cross-channel owner smoke
проверяет L0 после review/merge/release. Тесты здесь синтетические.
