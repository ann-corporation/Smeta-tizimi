## Короткий вывод

**Не создавать второй складской журнал.** `t2_sklad_harakat` уже является движением, `t2_sklad_qoldiq` — текущим остатком, а независимый склад и связи `t2_sklad_bog` уже существуют. Но сегодня это не согласованная модель физического склада: движение обязательно привязано к объекту, а независимый склад лишь агрегирует остатки связанных объектов. Ключ остатка не включает ни склад, ни единицу. Повтор операции и сторно имеют пробелы.

Старые строки оставить читаемыми и сверить/сопоставить до переключения чтений. Не распределять центральный склад по всем связанным объектам автоматически.

## Подтверждённые gaps и риски двойной истины

1. **Складская локация не входит в журнал/остаток.** Inventory: `t2_sklad_harakat.obyekt_id NOT NULL`; у журнала нет `sklad_id`. `t2_sklad_qoldiq` тоже объектный. Вместе с `t2_sklad_mustaqil` + M:N это даёт складской обзор, но не отдельное физическое количество центрального склада.
2. **Единица не входит в уникальность остатка.** `t2_sklad_qoldiq` уникален по `(obyekt_id, nomi)`, хотя обе таблицы хранят `birligi`. Совпавшее имя с разными единицами может слиться в одну строку остатка; в текущем RPC блокировка и обновление тоже ищут объект + имя.
3. **Повтор не гарантирован.** `operation_id` у движения nullable и в snapshot нет уникального ограничения. `t2_skladga_yozish` ищет любой `operation_id` без `kompaniya_id`; клиент `sbSkladgaYozish` создаёт новый id при каждом вызове, если повторно не передан тот же id. UI поэтому не доказывает safe retry после сетевого обрыва.
4. **Нет модели сторно связи.** В журнале есть `holat`, но нет ссылки на отменяемое движение/уникальности сторно. Обычный складской RPC увеличивает/уменьшает кэш и добавляет движение; M-29 отмена меняет `holat` движений и вручную возвращает остаток. Для общего журнала это отдельные пути изменения истины.
5. **В vocabulary расходится архитектурный контракт и фактическая схема.** E3 §4.5 описывает `t2_ombor_kirim_yuk_v1` и `operatsiya='kirim'`; локальный route map указывает `skladga_yozish → t2_skladga_yozish`, inventory допускает `prixod/rasxod`. До изменения E3/RPC нужен один mapping/источник контракта, а не параллельный writer.
6. **Текстовый поставщик вместо подтверждённой ссылки.** Журнал хранит `postavshik` как текст. Coordination требует связь поставщика с `t2_kontragent` по ИНН; текущий schema snapshot не показывает FK в движение.
7. **История источника отсутствует в движении.** Coordination требует для каждого импортированного движения file/document id, sheet и row. В schema snapshot у `t2_sklad_harakat` есть `izoh/manba`, но нет подтверждённых колонок source document/sheet/row.
8. **Текущий UI не соответствует целевому мобильному сценарию.** `/admin/logistika` — вкладки заявки/склад/контрагент/биржа/alias. `TestSklad` — консолидация, остатки, история, M-29 и форма; запись требует имя/единицу/количество и идёт через прежний writer. Координация задаёт отдельные простые действия «KELDI / BERDIM / QOLDIQ», телефон первым, ≤3 шага.

## Предлагаемая фазировка

### C11.0 — этот sidecar

Утвердить физическую границу склада, ключ материала/единицы, учёт старых движений, сторно и переход M-29. L0/владелец решают, какая связка склада с объектом разрешает приём/выдачу. Никаких production writes сейчас.

### C11.1 — модель и RPC

- Оставить `t2_sklad_harakat` единственным ledger; новых параллельных таблиц правды не добавлять.
- Кандидатные **additive** изменения существующих таблиц (после проверки накопленных данных/коллизий): в движении — nullable legacy-safe `sklad_id`, supplier FK на `t2_kontragent`, source `document_id/sheet/row`, `storno_of_id`, а также связь с заявкой/заказом/строкой M-29 при наличии; у остатка — тот же stock-location scope и `birligi` в уникальном ключе. Сохранить `postavshik` как исходный текст-снимок, не как идентификатор.
- Новый версионированный RPC требует `operation_id`, сверяет `(kompaniya_id, operation_id)` и отпечаток запроса: совпавший retry возвращает исходную квитанцию, тот же id с иным payload — conflict. Локировать одинаковый ключ остатка до проверки/изменения.
- Приход/расход и transfer записывать атомарно. Transfer — пара `rasxod` исходного склада + `prixod` целевого склада с общим transfer correlation; M:N link лишь разрешает маршрут/видимость. Запас не размножается по связанным объектам.
- Storno в пределах утверждённых 24 часов — компенсирующая строка противоположного направления, с ссылкой на исходную строку, причиной, actor и временем; повтор сторно идемпотентен, второе сторно той же строки запрещено. Движения не удалять и не переписывать. Остаток — сумма журнала; кэш сверяется с ним.
- Перевести `m29_bajar_v1` / `m29_bekor_v1` на те же invariant-и внутри транзакции. M-29 остаётся `rasxod`; его document/status lifecycle не превращать в приходной документ.
- До cutover: read-only отчёт коллизий `(obyekt_id, nomi)` по `birligi`, повторных/null operation IDs, неоднозначных склад↔объект связей и расхождений journal vs balance. Backfill только по доказуемым связям; неизвестное оставить неопределённым и вынести на ручное решение.

### C11.3a — Navoiy омбор дафтари, только лист «Приход»

Использовать только лист `Приход`; остальные листы, включая копию, расход и остаток, не импортировать как транзакции. Оригинал — через document registry/R2; preview показывает новые/дубликаты/ошибки, нормализацию имени/единицы только как предложение. Ключ из coordination: склад + дата + нормализованное имя + единица + количество + поставщик/получатель + исходная строка. Имя кирилл/латин и aliases не объединять автоматически. Сначала read-only профиль и preview; проведение — отдельное подтверждение после C11.1. Ранее заданный файл «Остаток» теперь не контрольная истина; отображать только если владелец отдельно просит сравнение, без метки ошибки. Расходы из книги не загружать; пока их нет, UI говорит «расход ещё не введён», а не «полный конечный остаток».

### C11.3 — реестр 1С, затем C11.2 / C11.4

1С-приходной реестр — отдельный parser/preview и дубликат-контракт. Поставщика сопоставлять по нормализованному точному ИНН с `t2_kontragent`; неоднозначность — ручная. Сумма/цена/количество/НДС исходника сохраняются раздельно; НДС не выводить из догадки и не смешивать с физическим количеством. Предложение распределить по объектам — только draft с объяснимой уверенностью и явным подтверждением, не запись. Затем мобильные KELDI/BERDIM/QOLDIQ; desktop и Excel export для снабженца/бухгалтера — после стабилизации модели.

## Синтетические acceptance-сценарии

1. Приход цемента в независимый центральный склад: один receipt, правильный склад+единица, повтор того же operation id не удваивает qoldiq.
2. Выдача арматуры мастеру на объект: остаток уменьшается только в выбранной локации; предупреждение «нет прихода»/нехватки видно, явное разрешение проверяется сервером.
3. Перенос между центральным и объектным складом: обе строки атомарны, общая корреляция, суммарное количество по компании не меняется; два связанных объекта не получают двойной остаток.
4. Сторно прихода/выдачи: только с причиной и полномочием; ровно одно компенсирующее движение; повтор не удваивает обратный эффект; история оригинала остаётся видимой.
5. M-29 расход и отмена используют тот же журнал; после отмены нет различия между ledger-derived balance и кэшем.
6. Повторное выполнение одного импортного листа: те же source rows дают duplicate review; две одинаковые legit строки с разными исходными номерами не схлопываются. Импортируются только строки «Приход».
7. Один материал с одинаковым именем, но разными единицами остаётся двумя ключами; конфликт старых строк попадает в reconciliation report, а не теряет количество.
8. Отвязка склада от объекта меняет доступ/видимость, но не стирает историю и не перераспределяет остаток. Повторные активные связи не суммируют одну и ту же локацию дважды.
9. Поставщик с точным INN связывается с существующим `t2_kontragent`; пустой/неоднозначный INN остаётся pending. Оригинальный файл и каждый импортный row ref доступны по document id/sheet/row.
10. Роль без `warehouse.receive/write` не видит/не выполняет запрещённое действие; tenant leakage и повтор с тем же operation id в двух компаниях исключены.
11. На 360 px три основные кнопки, крупные зоны нажатия и не более трёх шагов; худшая сеть не теряет зафиксированный operation id и показывает состояние отправки/повтора.
12. Read-only schema/profile и preview не меняют таблицы или остатки. Любая итоговая сверка синтетическая; owner smoke — отдельный gate.

Нужен nullable object при обязательном warehouse scope новых команд; старые object-only записи остаются читаемыми. Такое ослабление NOT NULL и перевод читателей — отдельная явно reviewed часть migration, не молчаливый backfill.
3. Новый физический остаток — производная одного журнала по tenant/warehouse/material identity/unit. Не создавать новый mutable stock table. Legacy object cache не выдавать за физический остаток центрального склада; до cutover сверить его с legacy журналом.
4. BERDIM и M-29 не могут списывать один и тот же материал дважды. Центральный склад→объект — атомарный transfer (две связанные строки), выдача в работу/M-29 — одно физическое списание с document coverage. Mobile BERDIM нельзя запускать до acceptance этого контракта. Текущие M-29 writer/cancel не переписывать в receipt-preview PR.
5. Повтор зависит от tenant+operation_id+неизменного payload; импорт дополнительно проверяет business/source key. Две одинаковые позиции на разных исходных строках сохраняются двумя движениями. Изменённая строка уже принятого документа требует review/коррекции, а не молчаливого второго прихода.
6. 24-часовое storno — отдельная обратная строка с единственной ссылкой на original; original остаётся неизменным. Не ограничиваться `holat='bekor'` и ручным изменением кэша.
7. Книга без цены не создаёт денежный расход. Реестр1C может предложить enrichment по поставщику/дате/материалу; совпадение текста не доказывает равенство позиции и не проводит повторный физический приход.
8. Существующая `document.write` — текущая граница legacy warehouse gateway. `warehouse.receive/write` выше — только кандидат будущих granular прав, не доступное сейчас разрешение. Новое полномочие должно появиться в единой роли/сервере; UI не авторизация.

### Контракт первой поставки C11.3a

Отдельный receipt-only parser сохраняет source hash/sheet/physical row, неизвестные деньги NULL, отмечает неполные строки, date-formatted quantity и источниковые формулы. Формат даты в количестве нельзя незаметно превратить в serial quantity. Полупустые заготовки с одним типом/поставщиком не превращаются в движения. Только подтверждённая вкладка Приход; Остаток/Расход/копии не oracle и не movement.

Сначала доступен честный preview; проведение, создание склада и original R2 registration будут подключены отдельным reviewed model/RPC PR. Preview не выдаётся за импорт и не показывает фиктивную кнопку сохранения. Migration требует rollback/negative acceptance и L0 применения, не запускается этим PR.
